# Как работает хук карты для Geely Xingrui L

[`xingrui_l.js`](./xingrui_l.js) - это Frida-агент, который преобразует внутренние навигационные данные картографического приложения Geely в протокол AutoDisplay. Он предназначен для процесса `com.geely.map` и представляется принимающей стороне как провайдер и профиль автомобиля `geely_xingrui_l`.

В широком смысле его задача совпадает с задачей [`l7.js`](./l7.js): наблюдать за работой штатной карты, не подменяя расчет маршрута, собирать уже существующее внутри приложения состояние навигации и передавать его другому процессу на головном устройстве. Однако одинаковым у двух скриптов остается прежде всего формат результата. Внутреннее устройство карт отличается, поэтому путь к этим данным у Xingrui L построен совершенно иначе.

L7 в основном читает высокоуровневые Java-объекты Flyme Auto. Xingrui L одновременно использует нативный перехват в `libGbl.so`, Java-callback'и Presenter, данные инерциальной навигации, внутренний JSON-протокол, кэш маршрутов и периодическую проверку состояния навигации. Именно сочетание этих источников определяет архитектуру файла.

## Структура файла и среда выполнения

В собранном файле 16 166 строк. Как и в `l7.js`, первые 13 652 строки относятся не к конкретному автомобилю, а к встроенной среде выполнения: Frida Java Bridge, Android ART и JNI, совместимым функциям Node.js и оберткам загрузки модулей.

Модуль Xingrui начинается с [`xingrui_l.js:13653`](./xingrui_l.js#L13653) и сохраняет имя исходного файла `hook_geely_map_overlay_widget.js`. Его собственная часть занимает около 2 514 строк, тогда как автомобильная часть L7 содержит примерно 1 375 строк.

Основные параметры объявлены в [`xingrui_l.js:13661`](./xingrui_l.js#L13661):

| Параметр | Значение |
| --- | --- |
| Пакет карты | `com.geely.map` |
| Провайдер | `geely_xingrui_l` |
| Профиль автомобиля | `geely_xingrui_l` |
| Адрес сокета | `127.0.0.1:23791` |
| Версия протокола | `1` |
| Система координат | `gcj02` |
| Версия хука | `2026.07.07.auto-heartbeat` |
| Смещение нативного маршрута | `40063332` / `0x2635164` |

Весь модуль Xingrui запускается внутри `Java.performNow()`. Пустой интервал удерживает Frida-агент активным, а основной 25-миллисекундный рабочий цикл создается позже установщиком местоположения и сокета.

## Какие части действительно включаются

В файле описано больше вариантов перехвата, чем запускает текущая точка входа. Это важно учитывать: некоторые функции представляют собой полностью подготовленные запасные реализации, но в данной сборке они не устанавливают Hook автоматически.

Блок запуска в [`xingrui_l.js:16127`](./xingrui_l.js#L16127) активирует следующие компоненты:

1. `installRoutePointExportWhenReady(1)` - нативное получение маршрута.
2. `installLocationSocketExport()` - положение, сокет, heartbeat и обработка задач.
3. `installGuidanceWidgetExport()` - показ и скрытие полос.
4. `installRouteFocusExport()` - смена выбранного маршрута.
5. `installPresenterGuidanceExport()` - маневр и окончательное расстояние, показанное интерфейсом.
6. `installExternalInteractionProtocolExport()` - внутренние сообщения о светофоре.
7. `startNavigationStatePolling()` - начало, продолжение и завершение навигации.

В файле также есть установщики для `NaviController`, `DrivingLayer`, `NaviComponent` и нескольких менеджеров дополнительного экрана Geely. Текущий стартовый блок их не вызывает. Они используют общие функции преобразования и образуют готовые альтернативные пути, но в этой сборке не устанавливаются без отдельного вызова.

То же относится к JSON-парсеру навигационных подсказок и объектному парсеру обратного отсчета светофора: обе реализации присутствуют, но их установщики не входят в активный путь запуска.

## Общий поток данных

Работу активной конфигурации можно представить так:

```text
libGbl.so setPathInfosNative        -> полный маршрут и альтернативы
NmeaManager$1.onDrInfoUpdate        -> положение автомобиля
BaseNaviPresenter.onUpdateNaviInfo  -> маневр и названия дорог
DriveGuideInfoHolder                -> итоговое расстояние из интерфейса карты
NaviObserverRouter                  -> показ и скрытие полос
ExternalInteractionManager 80189    -> JSON светофора
NaviController.isNaving()           -> жизненный цикл навигации
                                      |
                                      v
                        преобразование и дедупликация
                                      |
                                      v
                        очереди задач и сообщений
                                      |
                                      v
                            TCP 127.0.0.1:23791
```

Большинство Java-хуков сначала вызывает оригинальный метод карты, затем удерживает Java-объект через `Java.retain()`, если он понадобится после завершения callback'а, и ставит короткую задачу в очередь. Очередь ограничена 120 элементами, а 25-миллисекундный цикл выполняет до восьми задач за один проход.

## Сокет и формат сообщений

Реализация соединения начинается в [`xingrui_l.js:15909`](./xingrui_l.js#L15909). Скрипт создает Java `Socket`, включает `TCP_NODELAY` и записывает UTF-8 через `BufferedWriter`.

Сообщения хранятся в `pendingSocketLines` в виде объектов с самой строкой, диагностической меткой и временем постановки в очередь. Максимальный размер очереди - 100 элементов. Если соединение временно отсутствует, строки остаются в массиве и следующий рабочий цикл снова пытается их отправить.

Верхний уровень протокола совпадает с L7:

| Префикс | Содержимое |
| --- | --- |
| `HELLO` | Данные процесса, карты, провайдера, автомобиля и версии хука |
| `PING` | Периодическое подтверждение активности |
| `LOC` | Компактная строка положения |
| `ROUTE` | JSON с состоянием маршрута |
| `GUIDE` | JSON с маневром или обновлением расстояния |
| `LANE` | JSON с конфигурацией полос |
| `TL` | JSON с состоянием светофора |

`HELLO` ставится в очередь после установки соединения. `PING` создается не чаще одного раза в три секунды. Один и тот же цикл с периодом 25 мс обрабатывает задачи, отправляет последнюю позицию, создает heartbeat и выгружает очередь сокета.

## Положение автомобиля

Активный источник положения устанавливается на [`NmeaManager$1.onDrInfoUpdate()`](./xingrui_l.js#L16105):

```java
com.autosdk.common.location.NmeaManager$1
    .onDrInfoUpdate(com.autonavi.gbl.pos.model.DrInfo)
```

Этот callback передает данные инерциального счисления пути. Скрипт читает:

- `drMatchPos` как основную позицию, уже привязанную к дороге;
- `drRawPos`, если привязанной позиции нет;
- `drMatchAzi` как основное направление;
- `drAzi` как резервное направление;
- `spd` как значение скорости.

Долгота и широта хранятся целыми числами и делятся на `1 000 000`. В результате получаются обычные координаты GCJ-02 в градусах.

В отличие от источника `LocInfo` в L7, используемый здесь `DrInfo` не передает индексы текущего сегмента, Link и точки маршрута. Поэтому Xingrui записывает в эти три поля `-1`.

Callback не формирует отдельную строку для каждого обновления. Вместо этого он заменяет `pendingCarLocation` самым свежим объектом `DrInfo`. Каждые 25 мс цикл отправляет последнее еще не отправленное значение. Серия быстрых callback'ов таким образом объединяется, но самая новая позиция сохраняется.

Формат строки Xingrui:

```text
LOC|время|широта|долгота|направление|скорость|-1|-1|-1|1
```

В L7 после фиксированного поля `1` дополнительно идут версия протокола, провайдер, источник события и система координат. Формат Xingrui является более коротким вариантом того же сообщения о положении.

## Нативное получение маршрута

Основной маршрутный хук начинается в [`xingrui_l.js:14857`](./xingrui_l.js#L14857). Вместо ожидания высокоуровневого callback'а менеджера маршрутов скрипт находит `libGbl.so` и устанавливает перехват по адресу:

```text
база libGbl.so + 0x2635164
```

В коде эта точка называется `setPathInfosNative`. Поиск библиотеки повторяется раз в секунду до 30 раз, поэтому `libGbl.so` может загрузиться уже после запуска Frida-агента.

На входе в нативную функцию перехватчик получает указатель JNI-окружения, список атрибутов маршрутов и индекс выбранного варианта. Скрипт вручную создает небольшой набор JNI-функций:

- `GetObjectClass`
- `GetMethodID`
- `CallObjectMethodA`
- `CallIntMethodA`
- `CallLongMethodA`
- `GetFieldID`
- `GetObjectField`
- `GetIntField`

С их помощью хук обходит Java-список, не используя в этой точке высокоуровневые обертки Frida Java.

Для каждого пути читаются:

- `getPathID()`
- `getLength()`
- `getTravelTime()`
- `getTrafficLightCount()`
- `getTollCost()`
- `getSegmentCount()`
- списки координат всех Segment и Link

Каждый маршрут превращается в объект с полями `index`, `selected`, `pathId`, `length`, `travelTime`, `trafficLightCount`, `tollCost`, `signature` и `points`.

Геометрия маршрута имеет привычную структуру:

```text
PathInfo
  -> SegmentInfo
       -> LinkInfo
            -> Coord2DInt32 [lon, lat]
```

Сначала скрипт читает точки всех Link. Если внутри сегмента не удалось получить ни одной точки Link, используется `SegmentInfo.getPoints()`.

Активный нативный payload имеет следующую форму:

```json
{
  "ts": 0,
  "source": "native:setPathInfosNative:selected-live",
  "navigating": true,
  "selectIndex": 0,
  "routeCount": 3,
  "pointCount": 1234,
  "routes": []
}
```

Во время работы подставляются фактическое время, состояние навигации, счетчики и массив маршрутов. В payload входят все пути из нативного списка, а не только выбранный.

Нативный построитель добавляет целые поля `lon` и `lat` непосредственно в массив `points`. В отличие от `normalizeCoordinate()` в L7, на этом этапе они не делятся на коэффициент и не переводятся в градусы. При этом отдельный канал местоположения делит координаты на `1 000 000`.

## Кэш маршрута и переключение варианта

Каждый пригодный payload сохраняется в `lastRoutePayload`. Нативные данные дополнительно копируются в `nativeRoutePayload`. Благодаря этому при смене выбранного маршрута не нужно заново обходить все Segment и Link.

Три активных Hook реагируют на выбор маршрута:

| Hook | Способ выбора |
| --- | --- |
| `RouteCarResultData.setFocusIndex(int)` | По индексу в списке |
| `NaviPresenter.suggestChangePathID(long)` | Поиск в кэше по `pathId` или `naviId` |
| `NaviPresenter.switchAlternateRoute(..., int)` | По индексу альтернативного пути |

`cloneNativeRoutePayloadWithSelection()` создает глубокую копию кэшированного JSON, обновляет `selected` у каждого маршрута, меняет `selectIndex`, устанавливает `navigating=true`, пересчитывает `pointCount` и отправляет новое состояние.

Отпечаток маршрута строится из идентификаторов выбранного пути, длины, времени, количества светофоров, стоимости, общего числа точек, сигнатуры и первой, средней и последней пары координат. Опрос состояния навигации использует этот отпечаток для определения изменения активного кэша.

## Сохраненные Java-реализации маршрута

Начиная с [`xingrui_l.js:15049`](./xingrui_l.js#L15049), в модуле находится второй, высокоуровневый Java-механизм чтения маршрута. Он понимает `PathInfo`, `NaviPath`, `RouteCarResultData` и разные контейнеры списков путей, используемые интерфейсом Geely.

Его вспомогательные функции умеют искать текущий маршрут в нескольких местах:

1. `ModuleServiceUtils.getDriveService().getRouteCarResultData()`.
2. `RouteRequestController.getInstance().getmCarRouteResult()`.
3. `driveService.getNaviPathInfo()`.
4. `NaviController.getInstance().getNaviPath()`.

В файле также полностью реализованы установщики для:

- двух перегрузок `DrivingLayer.drawRoute()`;
- `NaviController.onMainNaviPath()`;
- `NaviController.setNaviPath()` и `startNavi()`;
- `NaviComponent.drawRoute()`, `setNaviPath()` и `setRoute()`;
- маршрутных методов `ExtraScreenManager`, `WidgetExtScreenManager` и `HudExtScreenManager`.

Текущая точка входа эти установщики не вызывает. Они образуют готовый Java-слой альтернативного получения маршрута и объясняют значительную часть разницы в размере между `xingrui_l.js` и `l7.js`.

## Навигационные подсказки

Основной активный Hook подсказок устанавливается в [`xingrui_l.js:14655`](./xingrui_l.js#L14655):

```java
BaseNaviPresenter.onUpdateNaviInfo(ArrayList)
```

Callback удерживает как список навигационных данных, так и сам Presenter. В отложенной задаче он пытается вызвать `getmDirectionInfo()` у Presenter и использует полученный текст как приоритетное название следующей дороги поверх данных низкоуровневых объектов.

Как и L7, Xingrui может получить несколько объектов `NaviInfo`, а каждый из них - несколько панелей в `NaviInfoData`. Скрипт оценивает каждую панель:

- панель, выбранная `NaviInfoFlag`: +2;
- доступный идентификатор маневра: +8;
- непустое название следующей дороги: +6;
- доступное расстояние до маневра: +4;
- положительное расстояние до маневра: +1.

Наличие общего оставшегося расстояния и времени добавляет еще по одному баллу всему объекту `NaviInfo`. Для отправки выбирается контекст с наибольшей суммой.

Xingrui использует больше резервных полей ближайшего перекрестка, чем L7. Скрипт проверяет первый элемент `nextCrossInfo` и может взять из него:

- `maneuverID`
- `crossManeuverID`
- `outCnt`
- `curToSegmentDist`
- `nextRoadName`

Дополнительно используются `naviInfo.crossManeuverID` и `naviInfo.linkRemainDist`. Поэтому Presenter-путь может восстановить маневр даже при неполной основной панели.

Полный `GUIDE` содержит маневр, номер съезда с кругового движения, текущую и следующую дорогу, оставшееся расстояние и время маршрута, число оставшихся светофоров, индексы положения на маршруте, сведения о выбранной панели и `rawSegmentDistanceMeters`.

Одинаковые полные подсказки не отправляются повторно в течение 500 мс.

## Итоговое расстояние из интерфейса

В Xingrui есть второй канал `GUIDE`, которого нет в реализации L7. Он перехватывает:

```java
DriveGuideInfoHolder.updateNextRoadDistanceView(
    int distance,
    String[] textArray,
    int totalDistance)
```

Этот callback расположен близко к окончательному значению, которое карта выводит пользователю. Он отправляет небольшой частичный `GUIDE`:

```json
{
  "segmentDistanceMeters": 320,
  "totalSegmentDistanceMeters": 500,
  "finalSegmentDistance": true
}
```

Когда данный Hook установлен, обычное полное сообщение записывает в `segmentDistanceMeters` значение `-1`, а исходное расстояние панели сохраняет в `rawSegmentDistanceMeters`. Принимающая сторона может считать отдельное сообщение окончательного расстояния главным меняющимся значением, не теряя исходного контекста навигации.

Для частичных обновлений используется окно дедупликации 250 мс, поэтому расстояние может обновляться чаще, чем весь набор сведений о маневре.

## Резервный JSON-путь подсказок

В файле также реализована функция `sendGuideFromProtocolJson()`. Она умеет разбирать поля:

- `icon` и `newIcon`
- `roundAboutNum`
- `nextRoadName`
- `segRemainDis` и `nextSegRemainDis`
- `routeRemainDis` и `routeRemainTime`
- `routeRemainTrafficLightNum`
- `curRoadName`, `curSegNum` и `curPointNum`
- `etaText`

Такие сообщения получают признак `guideProtocol: true`. В текущей точке входа нет активного Hook, вызывающего этот парсер, поэтому он остается дополнительным протокольным адаптером рядом с основным Presenter-путем.

## Подсказки по полосам

Активные Hook полос устанавливаются на [`NaviObserverRouter`](./xingrui_l.js#L14702):

```java
onShowNaviLaneInfo(LaneInfo)
onHideNaviLaneInfo()
```

Callback показа удерживает объект `LaneInfo` и обрабатывает его асинхронно. Конвертер читает до 24 значений из массивов:

- `frontLane`
- `backLane`
- `extensionLane` с резервом `backExtenLane`
- `optimalLane`

Количество полос определяется как максимальная длина массивов front и back. Если `optimalLane` содержит пригодные значения, он формирует флаги `recommend`. В противном случае рекомендованными считаются элементы `frontLane`, отличные от `255`.

В payload передаются `show=true`, все массивы полос, логический массив `recommend`, `extensionLane` и пустые совместимые массивы `extFlags` и `tollGate`. Одинаковое состояние полос подавляется на 500 мс.

Callback скрытия отправляет `show=false` и `clear=true`, одновременно сбрасывая сигнатуру полос.

Алгоритм преобразования практически совпадает с L7. Отличается источник события: Xingrui использует `NaviObserverRouter`, а L7 - Flyme-класс `NaviObserverProxy`.

## Активный протокол светофора

Hook светофора устанавливается в [`xingrui_l.js:14620`](./xingrui_l.js#L14620) на две перегрузки:

```java
ExternalInteractionManager.buildDataAndDispatch(...)
```

Обрабатывается только протокол с идентификатором `80189`. Связанная с ним строка разбирается как JSON и преобразуется в сообщение `TL`.

Активный парсер читает:

- `trafficLightStatus`
- `redLightCountDownSeconds`
- `greenLightLastSecond`
- `dir`
- `waitRound`

Статусы преобразуются так:

| Исходный статус | Общий статус |
| --- | --- |
| `1` или `2` | `1` - красный |
| `4` или `5` | `4` - зеленый |
| `8` | `2` - переходное состояние |
| другое неотрицательное значение | `2` - переходное состояние |

Направления `1`, `2` и `4` сохраняются. Исходное направление `8` преобразуется в `4`, `7` - в `1`, остальные значения - в `-1`.

Для обратного отсчета сначала используется `redLightCountDownSeconds`, затем `greenLightLastSecond`. Результат содержит нормализованный и исходный статус, направление, номер цикла ожидания, сформированный идентификатор светофора и признак `trafficLightProtocol=true`. Поле `distanceMeters` равно `-1`, поскольку протокол `80189` не предоставляет отдельное расстояние ticker, которое получает L7.

Одинаковые сообщения о светофоре подавляются на 500 мс.

## Объектная реализация светофора

Еще один полный конвертер светофора находится в [`xingrui_l.js:14395`](./xingrui_l.js#L14395). Он умеет обрабатывать список из `NaviController.onUpdateTrafficLightCountdown(ArrayList)` следующим образом:

1. Находит элемент с `pathID` текущего навигационного пути.
2. Читает список `lightStates`.
3. Выбирает состояние, интервал `stime` - `etime` которого соответствует текущему времени.
4. При необходимости использует `lastSeconds`.
5. Читает направление, число ожиданий, идентификаторы Link, фазу и тип отображения.

Этот путь интерпретирует `lightType` со значениями `2`, `3` и `4` как красный, зеленый и переходный сигнал. Его установщик входит в `installNaviControllerGuidanceExport()`, который описан, но не запускается текущим блоком входа. Активным источником остается протокол `80189`.

## Жизненный цикл навигации

Официальное состояние навигации Xingrui определяет вызовом:

```java
NaviController.getInstance().isNaving()
```

Цикл начинается в [`xingrui_l.js:14825`](./xingrui_l.js#L14825) и выполняется раз в секунду.

При переходе из неактивного состояния в активное скрипт копирует последний кэшированный маршрут, устанавливает `navigating=true` и отправляет его как текущий навигационный путь.

Пока навигация остается активной, цикл сравнивает отпечаток маршрута с предыдущим активным отпечатком. Кэшированный маршрут отправляется снова, если отпечаток изменился или с предыдущего обновления прошло больше двух секунд.

При переходе в неактивное состояние кэши маршрута очищаются, после чего отправляется payload с `navigating=false`, нулевыми счетчиками и пустым массивом `routes`.

Состояние полос очищается собственным callback'ом скрытия. В модуле также имеются функции очистки подсказок и светофора, которые используются соответствующими каналами при получении пустого или скрытого содержимого.

## Последовательности основных событий

### Запуск навигации на Xingrui L

```text
Карта подготавливает объекты PathInfo
  -> нативный Hook setPathInfosNative строит и кэширует все маршруты
  -> NaviController.isNaving() меняется на true
  -> цикл копирует кэш с navigating=true
  -> ROUTE отправляется в AutoDisplay
  -> BaseNaviPresenter начинает формировать GUIDE
  -> полосы и светофор обновляют собственные состояния
```

### Переключение на альтернативный маршрут

```text
RouteCarResultData или NaviPresenter сообщает новый выбор
  -> создается глубокая копия нативного кэша
  -> обновляются selected и selectIndex
  -> пересчитываются pointCount и время
  -> измененный ROUTE отправляется принимающей стороне
```

### Обновление расстояния до следующего маневра

```text
BaseNaviPresenter передает маневр и названия дорог
  -> отправляется полный GUIDE
DriveGuideInfoHolder обновляет окончательное расстояние интерфейса
  -> отправляется малый GUIDE с finalSegmentDistance=true
  -> AutoDisplay объединяет устойчивый контекст маневра с меняющимся расстоянием
```

### Завершение навигации

```text
NaviController.isNaving() меняется на false
  -> кэши маршрута очищаются
  -> отправляется ROUTE с navigating=false и пустым списком
  -> скрытие полос и другие события содержимого очищают свои области
```

## Итог

`xingrui_l.js` удобнее всего рассматривать как многоканальный адаптер картографического стека Geely. Полный маршрут снимается рядом с нативной границей GBL, позиция приходит от наблюдателя инерциальной навигации, контекст маневра - от Presenter, окончательное расстояние - от держателя UI, полосы - от guide router, а светофор - из внутреннего JSON-протокола.

`l7.js` приходит к тому же протоколу AutoDisplay через более централизованную объектную модель Flyme Auto. Категории выходных данных специально сделаны похожими, но способы получения, представление координат маршрута, обработка жизненного цикла и сборка навигационной подсказки адаптированы к двум разным картографическим приложениям.
