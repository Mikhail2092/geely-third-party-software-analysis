# How the Geely Galaxy L7 Map Hook Works

[`l7.js`](./l7.js) is a Frida Java hook written specifically for the Geely Galaxy L7 and the Flyme Auto map application.

The easiest way to think about it is as a navigation data observer living inside the map process. The map continues doing its normal job, while the hook listens for important events, turns the map's internal Java objects into a compact protocol, and passes the result to another application running on the head unit.

It can export the matched vehicle position, active and alternative routes, turn-by-turn instructions, lane guidance, traffic-light countdowns, and navigation lifecycle events.

## Why the file is so large

The file is about 15,000 lines long, but most of it is not vehicle-specific logic. The first part contains the runtime bundled with the script:

- Frida Java Bridge
- Android ART and JNI support
- Node.js `Buffer` compatibility code
- Base64 and IEEE 754 helpers
- CommonJS and ESM loader wrappers generated by the bundler

The L7-specific code begins at [`l7.js:13653`](./l7.js#L13653). At the end of the file, `require_hook_flyme_l7_map_route()` starts that module.

## The basic flow

Once the script is injected into `com.flyme.auto.map`, it waits for the required Java classes to become available. It then replaces selected method implementations with Frida wrappers.

When the map calls one of those methods, the wrapper normally calls the original method first. After that, it reads the arguments or related map objects and prepares the data for export. In other words, the hook is designed to observe the navigation workflow while allowing the original map logic to continue running.

```text
Flyme Auto produces a navigation event
                |
                v
        Frida intercepts the method
                |
                v
    The hook reads and normalizes the data
                |
                v
       Data is placed in local queues
                |
                v
    A TCP connection sends it to the display app
```

## Local communication

The connection settings are defined at [`l7.js:13661`](./l7.js#L13661). The hook connects to:

```text
127.0.0.1:23791
```

This is a service running on the same head unit. The connection is output-only: `l7.js` writes UTF-8 messages but does not read commands from the socket.

Every message ends with a newline. The prefix tells the receiver what kind of data follows:

| Prefix | Meaning |
| --- | --- |
| `HELLO` | The hook has started or reconnected |
| `PING` | Periodic heartbeat |
| `LOC` | Current matched vehicle position |
| `ROUTE` | Active route and alternative routes |
| `GUIDE` | Upcoming maneuver and remaining journey data |
| `LANE` | Lane layout and recommended lanes |
| `TL` | Traffic-light state and countdown |

`ROUTE`, `GUIDE`, `LANE`, and `TL` carry JSON objects. `LOC` uses a smaller pipe-separated format so that frequent position updates remain lightweight.

## Vehicle position

The location hook is installed at [`l7.js:14695`](./l7.js#L14695) on:

```java
LocationInstrument.onLocInfoUpdate(LocInfo)
```

Whenever the map receives a new location, the hook reads the road-matched position rather than relying only on raw GPS coordinates. That makes the exported vehicle position follow the road geometry used by the navigation engine.

The exported values include:

- longitude and latitude from `stMatchRoadPos`
- road-matched course or bearing
- speed from `speedometer` or `speed`
- current segment index
- current link index
- current point index

The location line has this general shape:

```text
LOC|timestamp|latitude|longitude|bearing|speed|segment|link|point|1|protocol|provider|source|gcj02
```

The script accepts several coordinate storage formats. `normalizeCoordinate()` recognizes regular degree values as well as integer coordinates scaled by `1,000,000`, `10,000,000`, or `3,600,000`, and converts them back to ordinary longitude and latitude.

Position updates are limited to one message every 25 milliseconds, which gives a maximum rate of roughly 40 updates per second.

## Route extraction

Route conversion begins at [`l7.js:13912`](./l7.js#L13912). The hook reads Amap's `PathInfo` objects and builds a simpler route representation containing:

- path ID, path index, and navigation ID
- total distance and estimated travel time
- traffic-light count
- toll cost
- selected-route state
- complete route geometry

A navigation path is made of segments, and each segment is made of links. The hook walks through those levels and appends the coordinate points from every link. If a link does not expose its geometry, it falls back to the segment's own point list.

The route message contains the currently selected route together with any usable alternatives. This allows the receiving application to draw the active route and show the other options offered by the map.

Several map actions can schedule a fresh route export:

- a new route result is stored
- the driver switches to another route
- the focused route index changes
- guidance becomes active

Before exporting, the script confirms that navigation guidance is active. This separates an actual navigation session from ordinary route planning in the map interface.

To avoid sending the same large geometry repeatedly, the hook creates a route fingerprint from the identifiers, distance, duration, point count, and representative points from the beginning, middle, and end of the route.

## Turn-by-turn guidance

Guidance processing starts at [`l7.js:14257`](./l7.js#L14257) and is driven mainly by:

```java
NaviObserverProxy.onUpdateNaviInfo(ArrayList)
```

One update may contain several navigation objects, and each object may contain several guidance panels. The hook scores the available panels by looking for a maneuver icon, next-road name, segment distance, and the panel preferred by `NaviInfoFlag`. It then sends the panel with the most useful information.

The resulting `GUIDE` message can contain:

- maneuver icon ID
- roundabout exit number
- next road name
- current road name
- distance to the next maneuver
- remaining route distance
- remaining route time
- current segment, link, and point indexes
- diagnostic information about the selected guidance panel

There is also a fallback path at [`l7.js:14364`](./l7.js#L14364). The hook can parse `GuidanceTbtData(...)` messages printed by the map and recover the essential maneuver, road, distance, and time fields from the log text.

## Lane guidance

Lane processing begins at [`l7.js:14434`](./l7.js#L14434). It listens for the map's lane show and hide events and reads up to 24 lanes from the `LaneInfo` object.

The important arrays are:

- `frontLane`
- `backLane`
- `extensionLane` or `backExtenLane`
- `optimalLane`

If the map provides an explicit `optimalLane` array, the hook uses it to mark recommended lanes. Otherwise, it derives the recommendations from `frontLane`. A value of `255` is treated as an undefined lane value.

When the map hides the lane panel, the hook sends a clear message so that the receiving display removes the previous lane diagram at the same time.

## Traffic-light countdowns

Traffic-light processing starts at [`l7.js:14571`](./l7.js#L14571). For this Flyme Auto version, the information is recovered by hooking `FLogUtils.logi()` and watching selected messages produced by `GuidanceNsHelper`.

Two log events are used together:

- `onGuidanceTrafficLightTicker` supplies the distance to the traffic light
- `onGuidanceTrafficLightCountdown` supplies the state, direction, waiting round, and countdown

The hook converts the raw map status into the shared display protocol. Protocol status `1` is used for red, status `4` for green, and status `2` for another transition state. Red countdowns are stored in `redSeconds`, while green countdowns are stored in `greenSeconds`.

The `TL` message also includes the original status and direction values. That keeps the normalized data easy to consume while preserving the source values for diagnostics.

## Detecting the end of navigation

The hook can recognize the end of guidance through several map events:

- either overload of `IGuidanceAdapter.stopGuidance()`
- `RouteRequestManager.clearRouteCarResultData()`
- a route-state poll returning no current route result
- log messages containing `stopGuidance`, `stopNavi`, or the Chinese text for leaving navigation

When navigation ends, the script sends an empty route and clears the guidance, lane, and traffic-light states. This keeps every connected display synchronized with the map.

## Startup and runtime loops

Startup logic begins at [`l7.js:14872`](./l7.js#L14872). The script runs two small periodic loops.

The heartbeat loop maintains the local connection, sends a heartbeat roughly every three seconds, flushes queued messages, and can replay the most recent location after a reconnect.

The installation loop waits for the Flyme Auto classes, installs hooks as they become available, checks for a cleared route, and processes queued navigation tasks. This staged startup lets the script begin running before every map component has finished loading.

Taken as a whole, `l7.js` is a vehicle-specific adapter between Flyme Auto's internal navigation model and a small, consistent protocol understood by another application on the head unit. It leaves route calculation and guidance inside the original map while translating the resulting data into a form that an instrument cluster or auxiliary navigation display can use directly.
