## 3. Назначение программы

`[Подтверждено кодом]` AutoService — единый сервис адаптации свойств головного устройства. Он преобразует три нижележащих источника данных, Android Automotive VHAL, ECARX Car Signal и Mock в памяти, в единую модель `CarPropertyValue`, а затем предоставляет ее через AIDL/Binder программам верхнего уровня, таким как AutoAudio и AutoDisplay.

Его обязанности можно представить следующим образом:

```text
VHAL HIDL --+
            +-> JSON сопоставления профиля -> единый репозиторий свойств -> AIDL CarPropertyService
ECARX ------+                                                     +-> AutoAudio
Mock -------+                                                     +-> AutoDisplay
```

`[Подтверждено кодом]` AutoService не воспроизводит звуковые уведомления и не рисует приборную панель. Он отвечает за доступ к нижележащим сигналам, преобразование различий между моделями автомобилей, кеширование свойств, распределение подписок и единые операции чтения/записи.

| action | Ожидаемый способ вызова |
|---|---|
| `com.simplerbit.autoservice.action.BIND_CAR_PROPERTY_SERVICE` | Приложение верхнего уровня вызывает bindService |

## 6. Процесс запуска и работы

### 6.1 Обычный запуск

1. `[Обоснованный вывод]` На раннем этапе запуска процесса SecShell CP/AW считывает инкапсулированную нагрузку и создает точку входа приложения.
2. `[Подтверждено кодом]` `AutoServiceApplication` считывает `source_selection`.
3. `[Подтверждено кодом]` Создаются метаданные свойств, сопоставления и нижележащий источник данных для выбранного профиля автомобиля.
4. `[Подтверждено кодом]` Комбинация по умолчанию — `VHAL + FS11_A2`.
5. `[Подтверждено кодом]` При выполненном условии лицензии запускается `CarPropertyService`.
6. `[Подтверждено кодом]` Сервис создает приоритетное уведомление, записывает состояние выполнения и создает необязательную точку наложения размером 1px.
7. `[Подтверждено кодом]` После привязки программа верхнего уровня получает Binder `ICarPropertyService`.
8. `[Подтверждено кодом]` Каждый метод AIDL сначала проверяет пакеты и сертификаты, связанные с вызывающим UID, а затем переходит на уровень единых свойств.

### 6.2 Переключение источника данных/профиля автомобиля

1. В отладочном интерфейсе выбирается VHAL, ECARX или MOCK.
2. Выбирается профиль, совместимый с источником; MOCK может показывать все конфигурации профилей.
3. `AutoServiceApplication.a()` закрывает старый нижележащий источник.
4. Сохраняются новые `data_source` и `vehicle_profile`.
5. Считывается новый JSON сопоставления, перестраиваются менеджер свойств и нижележащий источник.
6. Сохраняется реестр подписок верхнего уровня.
7. Для уже подписанных свойств считываются и повторно распределяются текущие значения.

`[Подтверждено кодом]` Шаги 6 и 7 реализованы в `AutoServiceApplication.a()` повторным использованием старого диспетчера подписок `x` и обходом поддерживаемых свойств.

### 8.5 Поведение методов сервиса

Основная реализация: `defpackage.x5`.

- `getProperty`: считывает текущее кешированное/нижележащее значение из единого менеджера свойств.
- `getSupportedPropertyIds`: возвращает копию ID, поддерживаемых сопоставлением текущего профиля.
- `subscribe`: сохраняет Binder callback по propertyId; одинаковый Binder дедуплицируется ключом-оберткой.
- `unsubscribe`: удаляет callback, а при пустой коллекции удаляет запись свойства.
- `setProperty`: отклоняет null, отсутствующее свойство, доступное только для чтения свойство и значение несовпадающего типа.
- `setProperty`: после успешной записи на нижний уровень свойство `READ_WRITE` повторно считывается с нижнего уровня и обновляет единый репозиторий; чистое свойство WRITE обновляется записанным значением.

### 8.6 Допуск вызывающей стороны

`[Подтверждено кодом]` Каждый метод AIDL сначала вызывает `CarPropertyService.a()` для проверки Binder calling UID. Собственный UID сервиса разрешается сразу; внешний UID сопоставляется по имени пакета PackageManager и истории подписей.

| `com.simplerbit.autoaudio` | `FA:AF:CD:D5:A2:A4:03:F2:EB:F1:AA:B3:B2:6D:8B:02:9B:F8:A2:91` |
| `com.simplerbit.autodisplay` | `82:58:0C:CA:43:9E:7F:90:67:B2:A8:FC:08:E2:9F:F7:C5:BE:88:09` |

## 11. Источник данных VHAL

Основной класс: `defpackage.vo`.

### 11.1 Соединение

- `[Подтверждено кодом]` Напрямую вызывает `android.hardware.automotive.vehicle.V2_0.IVehicle.getService()`.
- `[Подтверждено кодом]` Это интерфейс HIDL/Binder Android Automotive Vehicle HAL 2.0.
- `[Подтверждено кодом]` Если сервис равен null или соединение завершается ошибкой, выбрасывается исключение инициализации, отображаемое отладочным интерфейсом.

### 11.2 Чтение

1. Согласно сопоставлению профиля единый propertyId преобразуется в `readSignalId`.
2. Создается `VehiclePropValue` с prop и фиксированным `areaId=0`.
3. Вызывается `IVehicle.get(value, callback)`.
4. Через `CountDownLatch` выполняется ожидание продолжительностью не более 2000 мс.
5. Нижележащее значение преобразуется в единый тип через `readTransform`.
6. Метка времени VHAL в наносекундах делится на 1,000,000 для получения миллисекунд; при отсутствии действительной метки используется локальное время.

### 11.3 Подписка

- `[Подтверждено кодом]` Используется `IVehicle.subscribe(IVehicleCallback, SubscribeOptions[])`.
- `[Подтверждено кодом]` Каждый `SubscribeOptions.propId` берется из сопоставления профиля.
- `[Подтверждено кодом]` `sampleRate=0.0f`, `flags=1`.
- `[Подтверждено кодом]` Нижележащий callback преобразуется, кешируется и передается соответствующему callback AIDL.

### 11.4 Запись

1. Проверяются режим доступа и тип единого свойства.
2. Нижележащее значение получается через `writeTransform`.
3. Создается VHAL `VehiclePropValue` с фиксированным areaId 0.
4. Вызывается `IVehicle.set()`.
5. Код возврата 0 считается успехом.
6. Затем свойство READ_WRITE повторно считывается с нижнего уровня, чтобы приоритет имело фактическое состояние автомобиля.

### 11.5 Специальные значения

`[Подтверждено кодом]` Для единых свойств 10037 (событие кнопки) и 10043 (запрос режима питания) список VHAL `int32Values` форматируется в строку, например `"[0,17,0]"`, используемую AutoAudio.

## 13. Источник данных Mock

- `[Подтверждено кодом]` Mock — источник свойств в памяти, не подключающийся к VHAL или Binder ECARX.
- `[Подтверждено кодом]` Единый интерфейс get/set/subscribe остается действительным.
- `[Подтверждено кодом]` Изменение свойства обновляет значение в памяти и запускает callback той же формы, что и реальный источник.
- `[Подтверждено кодом]` Отладочный UI предоставляет ползунки скорости автомобиля и оборотов двигателя и точку входа для записи любого свойства.
- `[Обоснованный вывод]` Поскольку верхний уровень по-прежнему получает тот же `CarPropertyValue`, Mock позволяет восстанавливать и отрабатывать бизнес-процессы AutoAudio/AutoDisplay без изменения клиентов.

## 14. Ключевые сквозные процессы

### 14.1 Чтение свойства

```text
клиент getProperty(10001)
  -> проверка вызывающей стороны x5
  -> проверка определения единого свойства
  -> чтение из текущего источника VHAL/ECARX/Mock
  -> readTransform
  -> CarPropertyValue(status/type/timestamps/value)
  -> возврат Binder Parcel
```

### 14.2 Подписка на свойство

1. Клиент вызывает `subscribe(propertyId, callback)`.
2. Сервис сохраняет Binder callback по propertyId.
3. Первая подписка запускает подписку на соответствующий нижележащий сигнал или добавляет его в filter.
4. VHAL/ECARX/Mock выдает изменение.
5. Сопоставление преобразует нижележащее значение в единое.
6. Единый репозиторий обновляет метку времени и состояние.
7. Для каждого callback этого propertyId вызывается `onPropertyChanged()`.
8. После отмены последнего callback соответствующую нижележащую подписку можно удалить.

### 14.3 Запись свойства

1. Клиент создает `CarPropertyValue`, задавая propertyId, valueType и соответствующее поле value.
2. Сервис проверяет наличие свойства, отличие от READ и совпадение типа.
3. `writeTransform` преобразует значение в формат нижнего уровня.
4. Выполняется VHAL `set`, ECARX `setProperty` или обновление Mock в памяти.
5. При ошибке возвращается false.
6. После успеха свойство READ_WRITE повторно считывается с нижнего уровня и распределяется, чтобы не подменять итоговое состояние автомобиля запрошенным значением.

### 14.4 События AutoAudio

1. AutoAudio явно запускает/привязывает CarPropertyService.
2. Вызывает `getProperty()` для инициализации текущей скорости, передачи, дверей и других состояний.
3. Вызывает `subscribe()` для 21 значения propertyId.
4. AutoService согласно профилю нормализует нижележащие signalId в фиксированные propertyId.
5. AutoAudio не требуется знать различия сигналов моделей; оно напрямую преобразует callback в звуковые уведомления и поведение кнопки громкой связи.

### 17.5 Первые 128 КиБ RC4 и инициализация ключа

Полная цепочка инициализации ключа для текущего образца:

1. `JNI_OnLoad` вызывает `setup_zipres` (`0x665C0`) по адресу `0x3C25C`.
2. `0x3C412` получает статическое поле `PKGNAME` через JNIEnv `+0x240` (сигнатура `Ljava/lang/String;`); `0x3C425` считывает объект поля, `0x3C442` получает строку UTF-8 через JNIEnv `+0x2A4`, а `0x3C455` копирует ее в 128-байтовый глобальный буфер `p403E47B6692945B1A4A3FA0625E24068` (VA `0x14FA40`).
3. `0x3C24D..0x3C253` передает этот буфер третьим аргументом `setup_zipres`; затем `0x66640..0x66650` копирует его по VA `0x150740`.
4. `0x6666C..0x666B7` создает на стеке фиксированное 16-байтовое начальное значение `66 97 6C E8 6D 46 38 B0 09 5A A5 D7 0F CB 9A A0`.
5. `0x666F0..0x6672F` ограничивает участвующую длину значением 16; `0x667C8..0x667D0` выполняет `seed[i] XOR source[i]`.
6. `0x66746..0x66764` записывает результат по VA `0x150510..0x15051F`.
7. KSA функции расшифровки `0x5F460` считывает ключ из VA `0x150510` по адресу `0x5F60B`; KSA находится в `0x5F608..0x5F644`, PRGA — в `0x5F660..0x5F6E5`.

Значение `PKGNAME` совпадает с именем пакета в Manifest: `com.simplerbit.autoservice`. XOR первых 16 байтов с начальным значением дает действительный ключ RC4 текущей нагрузки:

`05 F8 01 C6 1E 2F 55 C0 65 3F D7 B5 66 BF B4 C1`

Порядок алгоритма установлен: для `[0, 0x20000)` выполняется только RC4; для `[0x20000, EOF)` — только `XOR 0xAC`, дополнительный XOR к префиксу не применяется.

Обнаруженный ранее `p4B0...` не является действительным путем расшифровки этой нагрузки. Перед выполнением его mode фиксируется как big-endian `0x81DF6521`, а функция принимает только `0/1`, поэтому текущий вызов однозначно идет по default/no-op. `mthkey.sig` поступает только в отдельную цепочку выработки RC4 для именованного blob и не переопределяет приведенный выше ключ нагрузки. Поэтому вывод прежней версии отчета, в котором значения-кандидаты MD5/Фибоначчи из `p4B0...` считались еще не установленным ключом нагрузки, отменен.

### 17.7 Замыкание загрузки и регистрации Native

`[Подтверждено кодом]` Восстановлена следующая последовательность вызовов:

1. `JNI_OnLoad` инициализирует reader `gConfig` и получает поля, включая `classes0.jar`, его длину, `SecShell.dgc` и `classes.dgh`.
2. По адресу `0x3C25C` `JNI_OnLoad` вызывает `setup_zipres(char*, char*, char*, int)`, создавая контекст ZIP-ресурсов.
3. `open_zip_infile` имеет явные точки вызова по `0x64C45` и `0x64E38`; библиотека также экспортирует `open_zip_buffer`, охватывая файловый и находящийся в памяти ввод ZIP.
4. Последующий блок управления последовательно вызывает `loadDgg` и `doRegistern2` по `0x3FB52` и `0x3FB5A`.
5. `doRegistern2` восстанавливает имя класса `com/SecShell/SecShell/H1` и Native-метод `replace`; через таблицу функций JNIEnv `+0x18` вызывается `FindClass`, через `+0x35C` — `RegisterNatives`, число регистраций равно 1.
6. `find_dexfile`, функции совместимости создания ART 5.0/9.0 `DexFile`, `dvmJarFileOpen_stub`, операции ClassLoader и настройка разрешений памяти вместе образуют слой адаптации версий ART/Dalvik.

Эта цепочка взаимно подтверждает восстановленный JAR/DEX: имя `classes0.jar`, длина, расшифровка по смещению, контекст ZIP, загрузка DGG и перехват JNI относятся к одному процессу инициализации Native. Классы AW/AP/CP из Manifest по-прежнему отсутствуют в видимом и восстановленном DEX; следовательно, эти ранние прокси-точки входа предоставляет слой Native/внедрения SecShell, а не определяет непосредственно бизнес-DEX.

- 73 единых свойства автомобиля, их типы, состояния и режимы доступа.
- Дескриптор AIDL, пять транзакций сервиса, одна транзакция callback и порядок полей Parcelable.
- VHAL 2.0 get/set/subscribe, двухсекундное ожидание чтения и преобразование метки времени.
- Соединение ECARX `ecarxcar_service -> car_signal`, чтение/запись свойств и подписка SignalFilter.
- Протокол преобразования mapping/default/expression.
- Функции отладочного интерфейса для сервиса, свойств, Mock, исследования нижнего уровня, лицензии и обновлений.
- Публичные конечные точки лицензии, активации кодом и обновления и алгоритм подписи запроса.
- Самораспаковка NRV2D-8 библиотеки SecShell x86, 153 пользовательские релокации и ключевые символы загрузки Native.
- Полный сегментированный алгоритм `classes0.jar`: RC4 для первых `0x20000` байт, затем побайтовый `XOR 0xAC`.
- Начальное значение `setup_zipres`, инициализация XOR-ключа по имени пакета и итоговый ключ RC4 `05F801C61E2F55C0653FD7B566BFB4C1`.
- Полностью восстановленные JAR и DEX, ZIP CRC32, DEX SHA-1/Adler32 и стандартный/вспомогательный наборы исходного представления JADX.
- 839 class_defs и 802 Java-файла восстановленного DEX и связь их путей классов с видимым DEX.

### 20.2 Подтвердить невозможно

- Регистрирует ли каждое целевое головное устройство фактически сервис VHAL 2.0 или ECARX и какова соответствующая системная политика доступа.
- Значения в реальном времени и побочные эффекты каждого нижележащего signalId на фактической прошивке каждого профиля.
- Текущие ответы сервера на запросы лицензии, активации кодом и обновления.
- Влияние SecShell на распознавание подписи и межпакетную доступность Binder для текущих повторно подписанных образцов.
- Временные характеристики свойств, частоту callback и результаты выполнения автомобилем; для этого необходима динамическая среда, которую данный отчет не запускал.

## 21. Основные выводы

`[Подтверждено кодом]` AutoService — промежуточный слой автомобильных данных между приложениями головного устройства в этом проекте. 73 единых свойства и стабильный контракт AIDL изолируют различия моделей, поэтому клиенты AutoAudio и AutoDisplay понимают только фиксированные propertyId и не работают напрямую с signalId VHAL или ECARX.

`[Подтверждено кодом]` Ключевая реализация программы состоит из четырех частей: JSON-сопоставления профилей и легкие преобразования значений; три типа источников VHAL/ECARX/Mock; единый кеш свойств и диспетчер подписок; экспортированный Binder-сервис с условиями сопоставления вызывающего пакета/сертификата. Отладочная Activity охватывает переключение источника, чтение/запись/подписку свойств, внедрение Mock и исследование нижнего уровня.

`[Подтверждено кодом]` Точки AW/AP/CP SecShell в Manifest, статически восстановленная цепочка загрузки Native и полностью восстановленный `classes0.jar/classes.dex` вместе доказывают наличие этапа восстановления нагрузки оболочки до запуска приложения. Восстановленный DEX содержит 839 class_defs, а JADX выводит 802 Java-файла. Пути его классов почти полностью совпадают с видимым бизнес-DEX; дополнительных путей бизнес-классов, присутствующих только в нагрузке, не обнаружено.

`[Подтвердить невозможно]` Текущий повторно подписанный сертификат не совпадает со списком разрешенных клиентов. Восстановленный DEX не добавляет прокси-класс подписи, однако влияние слоя Native/раннего внедрения SecShell во время выполнения по чисто статическим результатам исключить нельзя. Поэтому отчет подтверждает связи AutoAudio/AutoDisplay на уровнях архитектуры и протокола, но не может по статическим образцам установить окончательное Binder-соединение этого набора APK на реальном головном устройстве.

## 22. Проверка восстановления пробелов JADX

Созданы четыре представления восстановленного DEX: default, show-bad-code, simple и fallback, каждое содержит 802 Java-файла. В default имеется 65 заглушек методов; в show-bad-code и fallback — 0; simple не обрабатывает только один сторонний вспомогательный метод рефлексии Fragment, который покрыт двумя другими представлениями.

Ключевые бизнес-методы `o4.<init>(...)`, `u8.e(...)` и `j5.k(...)` восстановили соответственно построение сопоставления профиля/источника данных, отладочный редактор свойств и логику сравнения номеров версий. Каждая заглушка default имеет как минимум одно доступное для аудита альтернативное тело метода; не осталось бизнес-методов, видимых только как заглушка `throw`.

Полное восстановление здесь означает возможность статического аудита инструкций DEX и потока управления. Оно не означает восстановления имен классов и переменных, комментариев до обфускации или исходного проекта, готового к непосредственной компиляции.
